Manual, functional and regression testing

Manual testing is where I learn how a product really behaves: who uses it, what the rules are and where it can go wrong. Here is how I work and what it looks like on the page.

The types of testing I run

  • Functional testing against business requirements and acceptance criteria.
  • Regression and smoke testing in every release cycle.
  • End-to-end testing across roles, workflows and business logic, including calculations.
  • UI and post-release testing, across browsers and devices.
  • Role-based access testing in systems with several user levels.

My process

  1. Read the requirements like a skeptic. Challenge assumptions and list the risks.
  2. Design test cases from the business requirements and acceptance criteria.
  3. Explore real user scenarios across roles and workflows.
  4. Log defects in JIRA with clear steps, expected and actual results, and evidence.
  5. Retest fixes, run regression, and close the defect.

Sample defect report

Withdrawal is created twice when Submit is double-clicked

Severity: Critical. Priority: High. Environment: QA, Chrome on Windows. Role: Player.

Steps: log in as a player with a balance of 100, open Withdraw, enter 50, double-click Submit quickly.

Expected: one withdrawal of 50 is created and the button locks after the first click.

Actual: two withdrawal requests appear in history and the balance drops by 100.

Evidence: a screen recording and the duplicate API calls from the network tab.

Suggested fix: disable the button on first click and make the endpoint reject duplicate requests.

Once a flow is stable I automate the core of it. See Playwright automation, and for checks beyond the UI, API testing.
